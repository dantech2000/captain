# Feature 0025: Extensions

- Milestone: M21
- Status: Implemented on macOS; the page and Update need a check by hand in the app
- Parity: Docker Desktop [extensions](https://docs.docker.com/extensions/extensions-sdk/) and the Rancher Desktop [Extensions](https://docs.rancherdesktop.io/ui/extensions) page
- Decision: [ADR 0011](../adr/0011-extensions.md)

## Goal

A user can install a Docker Desktop extension by its image reference, open its page in a Captain window, and remove it again. The page talks to Captain through `window.ddClient`, so extensions built with the Docker SDK work without changes.

## In scope

- An **Extensions** page. Its sidebar entry sits above Snapshots. The page has:
  - An Install card with an image reference field and an **Install** button. Enter works too. Under the field, an orange note says: "Extensions run code from their publisher on this computer and in the engine, with your permissions. Install only extensions you trust."
  - The installed list, sorted by title. Each row shows the title, the description, the image, and the publisher, with **Open** and **Remove…**.
  - The header shows the count, or the running step ("Pulling …", "Installing …", "Removing …") with a spinner.
- **Install** has two steps.
  1. A reference without a tag or digest gets the newest version tag of its repository (see **Tags** under Notes). Captain pulls the image only when the engine answers 404 for it; another inspect error fails the step, so Captain never claims an image it cannot prove was absent. It reads the labels and the image ID, and reads `/metadata.json` from that image ID. An image without the `com.docker.desktop.extension.api.version` label is refused, and an image this step pulled is removed again.
  2. A dialog asks before anything runs. It shows the image, the publisher (`org.opencontainers.image.vendor`, or "Unknown publisher" in orange), the website, whether the extension has a page, its backend, and its host binaries in orange, and repeats the trust note. **Install** then:
     - refuses an ID that has an `extension.json` already, or an image whose repository an installed extension in another folder has (for example one installed before IDs had a hash), with "<title> is already installed from <image>. Use Update to replace it." A folder without `extension.json` is left from a stopped install, and Captain deletes it,
     - copies `ui.dashboard-tab.root` to `~/.captain/extensions/<id>/ui`,
     - copies the `darwin` host binaries to `~/.captain/extensions/<id>/bin` and marks them executable (`linux` or `windows` on those platforms),
     - starts the backend, if any,
     - refuses to start when the folder has an `extension.json` that Captain cannot read, or when `.backup/<id>` is left from an update that did not finish, and names the path. A folder with no `extension.json` is left from an install that stopped, and Captain deletes it.
  - writes `extension.json` last, with the engine it was installed on. A failed install removes the folder and the backend's containers, and the image when step 1 pulled it; an image the engine had before stays. It removes the backend's volumes only when the project had no containers or volumes before the install.
  - **Cancel** removes an image that step 1 pulled. The dialog has no close button and ignores Escape, so Cancel is the way out.
  - This cleanup, and the one after a failed install or update, removes the recorded image ID without force, never the tag. A tag can move to another image while the dialog is open, and the engine refuses to remove an ID that another tag still names, so the user's images and tags stay.
  - Files come from the inspected image ID, not the tag, so a pull or a re-tag while the dialog is open cannot change what gets installed. The backend runs that image ID too when `vm.image` is the extension's own image.
- **Update…** on a row asks for a tag. The dialog looks up the newest version tag of the repository and fills it in, shows the installed image, and says "No version newer than <installed tag> is published" when the newest tag is not a later version than the installed one. An empty field means the newest tag too. **Check** pulls the extension's repository with that tag and compares the image ID with the installed one (`extension.json` records it; for older installs Captain reads it from the installed image before the pull). If the pull fails but the engine has that image, Captain uses it, so a locally built extension can update too.
  - The same image: a toast says the extension is up to date.
  - Another image: the install dialog asks again, titled "Update <title>?". It shows the installed and the new image with their `org.opencontainers.image.version` labels, in orange with "an older version" when the new version number is lower. It also lists the new image's backend and host binaries, since they may change.
  - **Update** closes the extension's window, copies the new UI, host binaries, and Compose files to `~/.captain/extensions/.update/<id>`, stops the old backend without `--volumes`, moves the old `ui`, `bin`, and `compose` folders and `extension.json` to `~/.captain/extensions/.backup/<id>`, moves the new ones in, writes `extension.json`, and starts the new backend. The ID stays the same. The backend's volumes and any other files in the extension's folder stay. Only after the new backend starts does Captain delete the backup and remove the old image: its old tag, or its ID when the pull moved the tag. A failure there only logs.
  - A failed update also removes the new image when Check pulled it and its image ID differs from the installed one.
  - If a step after the staging fails, Captain stops the new backend, puts the old files back, and starts the old backend on its image ID. If that fails too, the error says so and the backup stays. The old `extension.json` moves back over the new one in one rename, so the folder always has a manifest and the page still lists the extension with Remove. An update refuses to start while `.backup/<id>` exists, and names the folder.
  - An update runs to its end on a thread of its own that keeps the engine runtime alive. An engine switch during an update does not stop it between the file swap and the new backend's start or the rollback.
- **IDs.** The list reads only a manifest whose `id` is its folder's name. Captain builds paths and the Compose project name from the ID and deletes them on Remove, so an edited `extension.json` cannot point them elsewhere.
- **Engines.** `extension.json` records the engine as the `DOCKER_HOST` value or the `ssh://` URL from Settings. The page lists only the extensions of the connected engine. Update and Remove refuse an extension of another engine: "<title> was installed on <engine>. Connect to that engine to update or remove it." Installs from before this change have no engine; every engine lists them, and an update records the current one. Two `unix://` values are the same engine when their socket paths resolve to the same file, so a symlink such as `/var/run/docker.sock` matches the socket it points to.
- **Remove…** asks first. It closes the extension's window, runs `compose down --volumes` on the backend, deletes the folder and any `.backup/<id>` and `.update/<id>` left from an update, and removes the image. Open is off while an install, update, or removal runs, and Update and Remove close the extension's window again when they end.
- **Open** opens the extension in its own window, or brings the open one forward. The window has a GPUI title bar, a toast strip, and a `gpui-wry` web view. Open is off on Linux and Windows, and the page says why.
- The bridge answers the first SDK subset of ADR 0011: `extension.vm.service.get|post|put|patch|delete|head|request`, `extension.vm.cli.exec`, `extension.host.cli.exec`, `docker.cli.exec` (all three with `stream`), `docker.listContainers`, `docker.listImages`, `desktopUI.toast.success|warning|error`, `desktopUI.dialog.showOpenDialog`, `desktopUI.navigate.*`, `host.openExternal`, and `host.platform|arch|hostname`.
- **Navigate.** `desktopUI.navigate` has the methods of the SDK's `NavigationIntents` ([reference](https://docs.docker.com/reference/api/extensions-sdk/NavigationIntents/)): `viewContainers`, `viewContainer(id)`, `viewContainerLogs(id)`, `viewContainerInspect(id)`, `viewContainerTerminal(id)`, `viewContainerStats(id)`, `viewImages`, `viewImage(id, tag)`, `viewVolumes`, and `viewVolume(volume)`. Each brings the main window to the front. A container opens on the Project page of its sidebar entry with the inspector at Overview (`viewContainer` and `viewContainerInspect`), Logs, Terminal, or Stats. An extension backend that the lists hide opens on the Containers page: the inspector looks the container up among all containers, and the selection stays until another one is chosen or the setting hides backends again. An image or a volume is selected on its page. The engine inspects a named container, image, or volume first, and the promise rejects with "No container "<id>" exists" when there is none, as the SDK says. Another `navigate` method rejects as not supported. If the user closed the main window, the promise rejects and says so.
- **Extension containers stay out of sight.** Docker Desktop hides "containers created by extensions" from its container list until the user turns on **Show Docker Extensions system containers** ([settings](https://docs.docker.com/extensions/settings-feedback/)). Captain hides an extension's backend containers by default too, from the sidebar projects, the Containers page and its counts, the header tiles and engine card, the menu bar menu and the Dock badge, the problem and crash lights, ⌘K, the status bar's latest event, and the `captain mcp` tools. The **Containers** card on the Extensions page has a **Show extension containers** checkbox. It sets `show_extension_containers` (off by default) in the [settings file](../reference/settings.md#show_extension_containers), and applies at once in the app and on the next `captain mcp` call. Shown, each backend is its own Compose project in the lists. Storage reads the engine's disk use, so the images and volumes of a backend always count as in use and are never offered for cleanup. The extension's window talks to the engine through the bridge, so it sees its own containers either way.
- **The marker.** Captain sets the label `com.docker.desktop.extension=<id>` on every service of a backend, the proxy too. Docker's Resource Usage extension calls a container with that label key a system container (`isExtensionContainer` in its `useContainers.ts`, read from the source map in `docker/resource-usage-extension:1.0.4`), so its "System containers" count includes Captain's backends. Backends that Captain started before the label count by their Compose project name, `captain-ext-<id>`. A container that the list does not have yet, such as one in a `create` event, counts by its name, which Compose starts with the project name.
- **ddClient.** The SDK has no call about system containers ([DockerDesktopClient](https://docs.docker.com/reference/api/extensions-sdk/DockerDesktopClient/), [Docker](https://docs.docker.com/reference/api/extensions-sdk/Docker/)). `docker.listContainers` and `docker.cli.exec` return what the engine returns, extension backends included, which is what the Resource Usage count expects.
- **Pages served by the backend.** A `dashboard-tab.src` of `http://localhost:<port>` or `http://127.0.0.1:<port>` (or `https`) is a page the backend serves, as Portainer's `http://localhost:49000` is. The window loads that URL, and its origin takes the place of `captain-ext://<id>/` in the navigation policy. A `src` on another host does not open. The backend's published ports reach the Mac through Lima's port forwarding, and macOS App Transport Security does not apply to `localhost` ([NSAppTransportSecurity](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity)).

## Out of scope

- The deprecated v0 calls. Any other method rejects with "`<method>` is not supported by Captain".
- The marketplace, extension icons, and an allow list of images.
- Opening extension pages on Linux and Windows.
- `x-rd-install` and the other Rancher Desktop hooks.
- Hiding extension containers from the `docker` CLI, as Docker Desktop does. Captain does not stand between the CLI and the engine.
- One "Extensions" group for all backends when they show. Each backend is a Compose project, and the project actions work on it.

## Notes

- **Metadata.** `metadata.json` has optional `icon`, `ui`, `vm`, and `host` sections ([metadata](https://docs.docker.com/extensions/extensions-sdk/architecture/metadata/)). `vm` has an `image` or a `composefile`, and `exposes.socket`. `host.binaries` is a list of objects keyed by `darwin`, `linux`, and `windows`. `${DESKTOP_PLUGIN_IMAGE}` in `vm.image` means the extension image. Labels follow [extension labels](https://docs.docker.com/extensions/extensions-sdk/extensions/labels/).
- **Tags.** Docker asks extension publishers to tag images with semver so that Docker Desktop can find the newest version ([distribution](https://docs.docker.com/extensions/extensions-sdk/extensions/DISTRIBUTION/)), and many repositories, Docker's Disk Usage among them, have no `latest` tag. Docker Desktop is closed source; Captain does what Rancher Desktop does (`findBestVersion` in [manager.ts](https://github.com/rancher-sandbox/rancher-desktop/blob/main/pkg/rancher-desktop/main/extensions/manager.ts)). It lists the tags with the OCI distribution API, `GET /v2/<name>/tags/list` ([listing tags](https://distribution.github.io/distribution/spec/api/#listing-image-tags)), with an anonymous token from the `WWW-Authenticate` challenge ([token auth](https://distribution.github.io/distribution/spec/auth/token/)), following the `Link` header for more pages, as Rancher's [registry.ts](https://github.com/rancher-sandbox/rancher-desktop/blob/main/pkg/rancher-desktop/backend/containerClient/registry.ts) does. Docker Hub's API host is `registry-1.docker.io`, and a one-part name gets `library/`. The engine's own tags of the repository count too, so a locally built extension works without a registry. Captain picks the newest release tag (`1.2.3`, `v1.2.3`, or `v.1.2.3`), else the newest pre-release such as `1.0.0-rc.2`, and `latest` only when no tag is a version. Tags such as `main`, `pr-214`, or `test-1` do not count. A registry that cannot be reached only logs. The HTTPS client is `tokio-rustls` with the system's trusted certificates (`rustls-platform-verifier`), versions kube already builds.
- **IDs.** The ID is the repository without tag or digest, in lowercase, with other characters than letters and digits as `-`, then `-` and 8 hex digits of a 64-bit FNV-1a hash of the repository: `docker/disk-usage-extension` becomes `docker-disk-usage-extension-<hash>`. The hash keeps `acme/foo-bar` and `acme/foo_bar` apart. The ID names the folder, the `captain-ext://<id>/` host, and the Compose project `captain-ext-<id>`. Older installs keep their ID without a hash.
- **Copying files.** Captain creates a container of the image ID named `<id>-captain-copy` with the command `captain-copy`, which never starts, so images built `FROM scratch` work. It reads each path with the archive endpoint (`GET /containers/{id}/archive`) and removes the container with its anonymous volumes, which an image's `VOLUME` lines make at create. Only regular files and folders are unpacked; links are skipped, so no file points outside the folder.
- **Backend.** Captain writes `compose/captain-compose.json` and runs `docker compose -p captain-ext-<id> -f captain-compose.json up -d`. `compose down` runs in the same folder with the same `-f`, or in the temp folder when the file is missing, because without `-f` Compose looks for a file in the working folder and its parents. Each `compose` step is killed after 15 minutes. For `vm.image`, the project has one `backend` service. For `vm.composefile`, Captain copies the file's folder out of the image, as Rancher Desktop does. A Compose file at the image root, such as Portainer's `docker-compose.yml`, would copy the whole image, so there Captain copies the file and the files it names by a relative path: `.env`, `env_file`, bind mount sources, `extends.file`, `include`, and the files of `configs` and `secrets`. Compose includes nest ([include](https://docs.docker.com/reference/compose-file/include/)), so each copied `include` or `extends.file` is read too, and its paths count from its own folder (`ComposeWalk`). Paths that are absolute or use `..` are left out, each file is copied once, so a cycle ends, and the walk stops 8 levels below the root file. A named file the image does not have is skipped, and Compose reports it. Before this, a root Compose file copied nothing: the archive of `/` names its entries with a leading `/`, which the unpacker skips. Captain then runs `docker compose -p captain-ext-<id> config --format json` with `DESKTOP_PLUGIN_IMAGE` set, and edits the result. The `-p` names volumes and networks after the project, not after the `compose` folder that every extension has. Every service mounts the `guest-services` volume at `/run/guest-services` and restarts `unless-stopped`. With `exposes.socket`, a `captain-proxy` service (`alpine/socat:1.8.1.3`) forwards `127.0.0.1::8080` to the socket, as Rancher Desktop does with its own proxy ([extensions.ts](https://github.com/rancher-sandbox/rancher-desktop/blob/main/pkg/rancher-desktop/main/extensions/extensions.ts)). `vm.service` calls go to that published port as HTTP/1.1 with `Connection: close`; `vm.cli.exec` runs `docker exec` in the first backend service.
- **Exec.** `docker.cli.exec` runs the `docker` CLI with `DOCKER_HOST` set to the connected engine. The page's `env` is applied first and `DOCKER_HOST` after it, and `DOCKER_CONTEXT` is removed, in all three scopes. `docker.cli.exec` and `vm.cli.exec` refuse a `cmd` that is empty or starts with `-`, because the CLI reads global options such as `--host`, `-H`, `--context`, and `--config` only before the subcommand ([docker.go](https://github.com/docker/cli/blob/master/cmd/docker/docker.go) sets `SetInterspersed(false)`). They also refuse any `DOCKER_*` variable in `env` except `DOCKER_API_VERSION`, `DOCKER_BUILDKIT`, `DOCKER_CLI_HINTS`, `DOCKER_DEFAULT_PLATFORM`, and `DOCKER_HIDE_LEGACY_COMMANDS`, since `DOCKER_CONTEXT`, `DOCKER_CONFIG`, `DOCKER_CERT_PATH`, `DOCKER_CUSTOM_HEADERS`, and the TLS variables can pick another daemon or change what the client sends, and a variable that a later CLI adds may too ([environment variables](https://docs.docker.com/reference/cli/docker/#environment-variables)). `cwd` stays open: the page can name any host path in the arguments anyway. `host.cli.exec` runs the extension's own program, so only its `DOCKER_HOST` is fixed. `host.cli.exec` runs only a file named in the extension's `bin` folder, never a path. Captain drops one pair of matching quotes around each argument, because Docker Desktop runs these through a shell and extensions write `"{{json .}}"`. A plain exec resolves with `{cmd, code, stdout, stderr}` and the `lines`, `parseJsonLines`, and `parseJsonObject` helpers, and rejects on a non-zero exit. A streaming exec sends one reply per line, then the exit code; `close()` drops the call, which kills the process. On macOS and Linux the command runs in a process group of its own, and the kill reaches the whole group, so `docker compose` and `docker buildx` plugin processes stop too ([`process_group`](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html#tymethod.process_group)). Windows has no process groups; there only the `docker` process is killed.
- **List calls** return the Engine API's own JSON (bollard's `ContainerSummary` and `ImageSummary`). `filters` may be a JSON string or an object; a value may be a list or a map to `true`.
- **Web view.** GPUI Kit has no web view feature flag. The web view is the separate `gpui-wry` 0.7 crate on Longbridge's `lb-wry` 0.53.3; its only feature, `inspector`, turns on wry devtools ([WebView docs](https://github.com/longbridge/gpui-kit/blob/main/website/docs/webview.md), [example](https://github.com/longbridge/gpui-kit/blob/main/examples/webview/src/main.rs)). Captain builds the child view with `build_as_child` on the GPUI window, and sets devtools in debug builds only. The dependencies are for macOS only, so Linux CI needs no WebKitGTK.
- **Custom scheme.** `captain-ext://<id>/` serves files from the `ui` folder with a content type from the file extension. A path that leaves the folder gets 403; another host gets 404.
- **Isolation.** Each extension gets its own WebKit data store from `with_data_store_identifier`, with 16 bytes hashed from the ID (macOS 14 and newer; older systems use the default store). The navigation handler allows only the extension's own scheme and `about:`. Other links and `window.open` go to the system browser, and only `http` and `https` links open.
- **Bridge.** An init script (`captain-core/src/extension/bridge/shim.js`) defines `window.ddClient` and the `__ddMuiV5Themes` and `__ddMuiV6Themes` globals that `@docker/docker-mui-theme` needs, as Rancher Desktop does ([preload](https://github.com/rancher-sandbox/rancher-desktop/blob/main/pkg/rancher-desktop/preload/extensions.ts)). The theme package reads Docker Desktop's theme from these globals ([docker-mui-theme](https://www.npmjs.com/package/@docker/docker-mui-theme)); its version 0.0.9 still shipped that theme as a fallback, in `dist/packagedThemes.js`. There `MuiCssBaseline` pads the page body `16px 32px`, and the type scale uses 12px as the base size with a 14px `body1`. Extensions rely on that padding: without it, Logs Explorer and Resource Usage draw against the window edge. The shim's themes carry the same `MuiCssBaseline` padding and type scale. Pages that do not use MUI's `CssBaseline` keep their own layout, as in Docker Desktop. Each call posts `{id, method, params}` with `window.ipc.postMessage`. The window parses it, takes the extension from the window, and answers with `window.__captainBridge.resolve|reject|output|exit` through `evaluate_script`. The value types follow `@docker/extension-api-client-types` 0.4.2.
- **Toasts.** GPUI overlays cannot draw above the web view, so `desktopUI.toast` shows in a strip under the title bar. Success and warning go away after 5 seconds; errors stay until closed.
- **Main window toasts.** Every error toast in the app, extension errors included, comes from `widgets::error_notification`. It hides after gpui-kit's 5 seconds like the other toasts; gpui-kit fixes that time (`NotificationList::push` in gpui-component 0.7) and pauses it while the pointer is over the toasts. The message shows 3 lines; the full title and message go to captain.log. gpui-kit stacks toasts like Sonner, and an older toast peeks out below the newest at its own height, so a long error showed its tail under a short toast. The window shows one toast at a time (`NotificationSettings::max_items` is 1); an older toast with time left shows again when the newer one goes.
- **Code layout.** `captain_core::extension` has the metadata, labels, IDs, paths, the Compose project, the bridge messages and replies, the HTTP helpers, the shim, and the `ExtensionManager` trait. `captain-docker/src/extensions` has `DockerExtensions`. `captain-ui/src/extensions` has the page, its model and dialogs, and the macOS window in `window/`. The workspace gets the manager with the engine connection.

## Verification

Automated (`cargo test -p captain-core -p captain-docker`):

- Metadata parsing, labels, IDs (two repositories with the same slug get different IDs), the pinned image, the UI path mapping and content types, and the Compose project with its extension label.
- The marker: the label or the `captain-ext-` project name marks a backend. The container store hides backends from its lists and counts until `set_show_extensions(true)`; `show_extension_containers` defaults to false.
- The list holds only the extensions of the connected engine and older installs. An update's file swap rolls back to the old files, also when the new backend wrote its own `compose` folder.
- Tags: the newest release wins over junk tags and pre-releases, a pre-release only when there is no release, `latest` only without version tags; only a reference without tag or digest needs one. The registry address, the token URL of a challenge, and the next page.
- The files a root Compose file names, without absolute paths or ones that leave its folder. A page `src` on localhost loads as a URL, and one on another host does not open.
- Bridge routing: each method's route, the navigate intents, exec scopes and quote removal, service paths, unknown methods, list filters, the open panel options, and that Captain accepts every method the shim posts.
- Exec policy: a global option as `cmd` and daemon `DOCKER_*` variables are refused, `DOCKER_API_VERSION` is allowed, and `DOCKER_HOST` wins over the page's `env`. Install refuses an unreadable manifest or a leftover backup until Remove, and a repository that another folder holds; the list skips a manifest whose ID is not its folder. A failed rollback keeps a manifest in the folder. A symlinked socket path is the same engine.
- Replies, the host binary check, HTTP requests and responses (chunked and bare LF), and tar unpacking.
- The update reference (same repository, new tag) and the version comparison.

Live: `cargo test -p captain-docker --test live_extensions -- --ignored` on Captain Engine.

- Docker's Disk Usage extension (`docker/disk-usage-extension:0.2.9`, UI only), re-tagged `captain-agent-ext-ui`: install, `docker.cli.exec` plain and streaming, `docker.listImages`, a refused host binary, a refused `--host` before the subcommand, and remove.
- A backend extension built in the test, `captain-agent-ext-vm`: socat answers HTTP on `/run/guest-services/backend.sock`. It checks `vm.service` through the proxy and `vm.cli.exec`. A second install of the same repository is refused and the backend still answers. A manager for another engine does not list it and cannot remove it. An update to `captain-agent-ext-vm:broken`, whose backend image does not exist, fails; the old files, manifest, and backend come back and answer. Then it removes the extension.

`cargo test -p captain-docker --test live_extension_compose -- --ignored` installs Portainer's extension (`portainer/portainer-docker-extension:2.45.1`, a Compose file at the image root), checks that its page answers on `http://localhost:49000`, and removes it. It checks that `docker/disk-usage-extension` without a tag resolves to a version tag, and that `prepare` removes an image it pulled when the image is not an extension (`hello-world`). It passed on a test VM.

`cargo test -p captain-docker --test live_extension_host -- --ignored` (macOS) builds `captain-agent-ext-host:test` from scratch: a page and a `darwin` shell script `captain-agent-hello`. It installs it, checks that `bin/captain-agent-hello` is executable, runs it through `extension.host.cli.exec` in the bridge, and checks that a full path is refused. A check with the tag `test` says it is up to date. It then builds `captain-agent-ext-host:latest` (version 2.0.0), which exists only in the engine, checks for an update with the default tag, updates, runs the new script, checks that a file in the extension's folder stays and that the old image is gone, and removes the extension. Both live tests passed on a test VM.

A throwaway example opened the Disk Usage window with the web view on macOS: the page loaded from `captain-ext://`, ran `docker system df` through the bridge, and drew its chart.

By hand in the app, on macOS with Captain Engine:

1. Open **Extensions**. The page is empty and shows the trust note.
2. Type `docker/disk-usage-extension` and press Enter. The dialog shows the image `docker/disk-usage-extension:0.2.9`, the newest version tag. The header shows the pull. The dialog names Docker Inc. and says the extension has a page. Click **Install**. The row appears.
3. Click **Open**. A window titled "Disk usage" shows the chart. Click **Open** again; the same window comes forward.
4. Click **Update…**. The field fills in with the newest tag, and the dialog says that no version newer than 0.2.9 is published. Click **Check**; a toast says the extension is up to date.
5. Click **Remove…** and confirm. The window closes, the row goes away, and `docker images` no longer lists the extension.

6. Install `portainer/portainer-docker-extension:2.45.1`. Click **Open**; after a few seconds the window shows Portainer's page from `http://localhost:49000`.
7. Install `docker/resource-usage-extension` and open it. The title has space to its left. Click a "Go to containers" link; the main window comes forward on Containers.
8. With Portainer installed, the sidebar, the Containers page, the header counts, the menu bar menu, and ⌘K do not show `captain-ext-portainer-…`. Check **Show extension containers** on the Extensions page; the project shows at once with its two containers. Clear it again. Storage lists Portainer's image and volume as in use either way. In Resource Usage, "System containers" counts Portainer's two containers (a backend installed before the label needs Remove and Install first).
9. Install `acme/does-not-exist`. One error toast shows at most 3 lines, goes away after 5 seconds, and stays while the pointer is over it. Its full text is in captain.log.

Still open: a check against a public extension with host binaries, the third extension of the ADR's test set, and a live update of an extension with a backend.
